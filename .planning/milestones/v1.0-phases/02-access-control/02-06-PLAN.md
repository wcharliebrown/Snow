<objective>
Fix non-admin access to custom table data pages. Currently provisionCustomTable() registers
admin/data/* pages with required_permission='table_management', and admin-custom-table.php
has a matching inner guard — so non-admin users hit a 403 before the row-level ACL logic
ever runs. This plan introduces a new table_data_access permission, wires it into the
provisioner and the inner guard, migrates already-provisioned pages in the DB, and locks the
View Groups / Edit Groups selector widget to table_management users only.

Purpose: Makes the row-level ACL built in Phase 2 actually reachable by the non-admin users
it was designed for (UAT tests 6-9 were all skipped/blocked because of this gate).

Output:
  - table_data_access permission in seed data + live DB
  - provisionCustomTable() registers new data pages with table_data_access
  - Existing admin/data/* pages in the pages table migrated to table_data_access
  - admin-custom-table.php inner guard changed to table_data_access
  - View Groups / Edit Groups ACL widget hidden from users without table_management
  - POST guard prevents data-only users from overwriting ACL group values
</objective>

**Step A — Append migration section to database_schema.sql:**

```sql
-- =============================================================================
-- Phase 2 Gap Closure: table_data_access permission (2026-03-01)
-- =============================================================================
-- Separates "can access custom table data pages" from "can manage table definitions".
-- Non-admin users assigned table_data_access can reach admin/data/* and have row-level
-- ACL applied. table_management remains required for admin/tables (schema management)
-- and for the View Groups / Edit Groups selectors within each data form.

-- Add permission if not already present (idempotent)
INSERT IGNORE INTO permissions (name, description)
VALUES ('table_data_access', 'Access custom table data pages (row-level ACL applied)');

-- Migrate already-provisioned admin/data/* pages from table_management to table_data_access
UPDATE pages
SET required_permission = 'table_data_access'
WHERE path LIKE 'admin/data/%'
  AND required_permission = 'table_management';
```

**Step D — Guard POST collection for view_groups / edit_groups in the add POST handler
(lines 61-62) and edit POST handler (lines 98-99):**

Replace the unconditional collection of view_groups/edit_groups with a permission-gated
version that prevents a data-only user from overwriting ACL values via manual POST:

```php
// Only honour ACL group selections submitted by users with table_management
if (hasPermission('table_management')) {
    $viewGroupIds = array_filter(array_map('intval', (array)($_POST['view_groups'] ?? [])));
    $editGroupIds = array_filter(array_map('intval', (array)($_POST['edit_groups'] ?? [])));
} else {
    $viewGroupIds = null;  // sentinel: do not write these columns
    $editGroupIds = null;
}
```

Then in the rowData assembly before dbInsert (add) and dbUpdate (edit), only include
view_groups / edit_groups when not null:

```php
if ($viewGroupIds !== null) {
    $rowData['view_groups'] = !empty($viewGroupIds) ? implode(',', $viewGroupIds) : null;
}
if ($editGroupIds !== null) {
    $rowData['edit_groups'] = !empty($editGroupIds) ? implode(',', $editGroupIds) : null;
}
```

Apply this pattern to both the add POST block and the edit POST block. When a
table_data_access-only user saves, view_groups and edit_groups are simply absent from
$rowData, leaving the existing DB values unchanged.

Do NOT change: list view, canViewRow() call, canEditRow() call, delete handler,
formatGroupIds() call in the list table, or the $allGroups query (it is needed for
rendering when the user has table_management).
